REVIEWER FINDINGS — apply each finding's fix to the relevant section of
the prior plan; leave everything else untouched.

- [important] capabilities[5] (get-customer-points-status): X3: The widget GET route '/widget/points/status' declares `"customer_external_id": "identifier"` in its requestShape, but the widget cannot securely supply this value — it is a server-side identity that must be resolved from the authenticated session, not passed in by the caller. A caller-supplied customer_external_id opens a horizontal privilege-escalation path where one customer can query another's balance and discount code simply by changing the parameter. Fix: Remove 'customer_external_id' from the requestShape of GET /widget/points/status; the LLD should resolve the customer identity from the authenticated session context, not from a caller-supplied field.
- [important] capabilities[3] (generate-discount-code) and capabilities[4] (record-discount-grant): C2: The 'generate-discount-code' capability calls out to the Shopify Admin API to create a discount code but there is no paired write capability and no edge case that records the outcome when the Shopify call succeeds but the subsequent 'record-discount-grant' DB write fails. The edge case present covers the rollback direction (Shopify rejects → roll back debit) but not the opposite split-brain: Shopify accepts → app crashes before persisting the grant → the code exists in Shopify but the customer never sees it and a retry will generate a second code. Fix: Add an edge case explicitly covering 'Shopify discount code creation succeeds but the local record-discount-grant write fails before commit — on retry, the system must detect the already-created Shopify code (by idempotency key or lookup) and skip re-creation, then re-attempt only the local write.'
- [important] capabilities[4] (record-discount-grant), usesWorkflow flag: C5: 'record-discount-grant' has `"usesWorkflow": true`, but the discount_grants table's statusField is null and there is no stateMachine — meaning there is no declared lifecycle for this capability to own. The 'status' column on discount_grants represents an application workflow (pending → active → used/expired), and the spec reserves usesWorkflow=true for capabilities that own and write status transitions on a declared lifecycle. A capability that merely inserts the initial row (with an initial status) and never transitions it should be usesWorkflow=false; if a separate transition capability (e.g. mark-discount-used) is intended, it is missing from the plan. Fix: Either set usesWorkflow=false on 'record-discount-grant' (it performs an initial-state insert only) and add a separate capability that transitions discount_grants.status when the code is used or expires, OR confirm the insert-only intent and set usesWorkflow=false with no further change.
- [important] triggers[0] and edgeCases: T1: The external-event trigger for 'an order is paid' includes idempotency text on the trigger itself, but the edgeCases list addresses only the duplicate-delivery scenario for the balance/discount path. There is no edge case covering a duplicate delivery that arrives *after* a partial failure — e.g. the first delivery credited points but crashed before the debit/discount step; the second delivery finds a transaction row for the order and exits as a no-op, silently leaving the customer with a balance that should have triggered a discount. The deduplication anchor exits unconditionally on any existing transaction row, which conflates 'fully processed' with 'partially processed'. Fix: Add an edge case: 'Duplicate order-paid event arrives after a partial processing failure (credit recorded but discount generation incomplete) — the idempotency check must distinguish a fully-committed processing record from a partially-committed one, e.g. by checking both the point transaction row and the resulting discount_grants row before deciding no-op vs. resumption.'
- [minor] capabilities[2] (check-redemption-eligibility), dataNeeds: T2: The trigger's signalFields include `"order subtotal"` which is consumed by 'compute-points-earned', and `"customer external id"` which is consumed by 'record-points-credit' and 'get-customer-points-status'. However, the signal field `"order external id"` is listed on the trigger and is used by 'record-points-credit' and the idempotency check described in the dataFlow, yet no capability explicitly lists 'order external id' in dataNeeds for the idempotency guard step — the check is described only in the trigger's idempotency prose and in the edgeCases, leaving the LLD without a capability anchor to generate the guard logic against. Fix: Add 'order external id' to the dataNeeds of 'record-points-credit' (it already writes it to point_transactions) and ensure the idempotency pre-check is expressed as a dataNeed on a dedicated read capability or on 'record-points-credit' itself so the LLD has an explicit anchor for the existence check query.
