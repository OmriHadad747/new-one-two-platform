FINDINGS:
  - - [critical] capabilityRecipes.widget-apply-redemption.steps (try block, sql_transaction): The sql_insert for point_redemptions (step inside try→sql_transaction) has no ON CONFLICT clause, yet the table declares `uniqueConstraint: { columns: ["cart_external_id", "customer_external_id", "status"] }`. Per R1/Pattern A, an INSERT that is the primary write for a dedup key requires `ON CONFLICT (...) DO NOTHING RETURNING id` so concurrent retried POSTs cannot insert two active rows for the same (cart, customer). The pre-check SELECT earlier in the recipe is not atomic with this INSERT (race window between the SELECT and the INSERT), meaning two concurrent requests that both pass the SELECT can both reach this INSERT and create duplicate active redemptions and duplicate ledger debits. The template reads: `INSERT INTO point_redemptions (customer_external_id, cart_external_id, ...) VALUES (...) RETURNING id` — no conflict clause present. Fix: Change the point_redemptions INSERT template to `INSERT INTO point_redemptions (customer_external_id, cart_external_id, discount_code_node_id, discount_code, points_applied, discount_value_minor, currency, status) VALUES (${customerId}, ${cartId}, ${discountNodeId}, ${discountCode}, ${pointsRequested}, ${discountValueMinor}, ${currency}, 'active') ON CONFLICT (cart_external_id, customer_external_id, status) DO NOTHING RETURNING id`, then add a decision step after the INSERT that checks `newRedemption.length === 0` and returns 409 (duplicate), matching Pattern A.
- [critical] capabilityRecipes.credit-points-on-order-paid.steps[3] (sql_select idempotency check) and steps[7] (sql_transaction → sql_insert): The idempotency check is a plain SELECT followed later by an INSERT, not an atomic claim. The sql_insert inside the transaction reads `ON CONFLICT DO NOTHING` with no conflict target columns specified — `ON CONFLICT DO NOTHING` without a column list is syntactically valid in PostgreSQL only when a unique constraint or exclusion constraint exists on the table; the `point_ledger` table declares `uniqueConstraint: null`. There is no unique constraint on `(order_external_id, entry_type)` in the database schema, so the conflict target is unresolvable and the INSERT will error at runtime rather than silently dedup. Two concurrent deliveries of the same `orders/paid` webhook that both pass the SELECT (race window) will both attempt the INSERT and one will either fail or create a duplicate earn entry and double-credit the customer. Fix: Add `uniqueConstraint: { columns: ["order_external_id", "entry_type"] }` to the `point_ledger` table (filtered to non-null order_external_id rows, or accept the broader constraint) and change the INSERT template to `ON CONFLICT (order_external_id, entry_type) DO NOTHING RETURNING id`, then gate the upsert on `ledgerRow.length > 0` with a decision step inside the transaction, eliminating the pre-transaction SELECT entirely per Pattern A.
- [critical] capabilityRecipes.widget-apply-redemption.steps[try block]: shopify_mutation discountCodeBasicCreate → variables: The mutation variables map contains `"basicCodeDiscount": "$discountInput"` but no earlier step in the recipe binds a variable named `discountInput`. The recipe builds `discountCode`, `discountValueStr`, `discountValueMinor`, and `customerGid` in separate compute steps but never assembles them into a `discountInput` object. A codegen reading this spec will emit `variables.basicCodeDiscount = discountInput` which is undefined at runtime, causing the Shopify mutation to receive a null input and fail (or throw). Fix: Add a compute step before the try_catch that assembles the Shopify input object — e.g. `expression: "({ title: 'Points redemption', code: discountCode, startsAt: new Date().toISOString(), appliesOncePerCustomer: true, usageLimit: 1, customerGets: { items: { all: true }, value: { discountAmount: { amount: discountValueStr, appliesOnEachItem: false } } }, customerSelection: { customers: { add: [customerGid] } } })"` with `bindResultTo: "discountInput"`, then reference `"$discountInput"` in the variables map.
- [important] capabilityRecipes.admin-get-customer-balances.steps (four decision branches): The four sequential `decision` steps each write to `balanceRows` inside their `ifTrue` branches, but per BIND SCOPING rules, a `bindResultTo` set inside `decision.ifTrue` is only visible within that branch — it is NOT visible at the outer recipe scope. The downstream steps (`hasNextPage`, `pageItems`, `nextCursor`, `response`) reference `balanceRows` at the top level, where it was never bound. A codegen implementing the scoping rules correctly will emit a reference to an undefined variable `balanceRows` for the pagination compute steps. Fix: Hoist a single mutable `balanceRows` binding at recipe scope by restructuring as nested decisions (if cursor && search → … else if cursor → … else if search → … else …) using a single decision tree whose every leaf sets the same outer `bindResultTo: "balanceRows"`, or declare `balanceRows` via a prior compute step initialised to `[]` and have each branch perform a sql_select with a distinct `bindResultTo` name, then merge with a final compute step before the pagination logic.
- [important] capabilityRecipes.widget-apply-redemption.edgeCases[1]: The stated edge-case mitigation reads: "orphaned discount from first attempt is left unreferenced and will be detected by monitoring stale discount_code_node_ids." This contradicts the HLD edge case which requires: "the system must detect the orphaned discount on retry, void it, and restart the redemption cleanly rather than issuing a second discount." The plan acknowledges the gap but provides no recipe steps to void the orphaned discount — the orphaned Shopify discount code remains permanently active and usable by the customer as a free discount, constituting a financial integrity defect. Fix: Add a step in the widget-apply-redemption recipe (after the existing active-redemption conflict check returns 409) that queries point_redemptions for a row with matching (cart_external_id, customer_external_id) and status='active' but a NULL discount code or a mismatch, and if found issues a discountCodeDeactivate mutation before allowing a new redemption to proceed; alternatively document this as a platformGap with a sweep cron that voids discount_code_node_ids with no matching active redemption row.
