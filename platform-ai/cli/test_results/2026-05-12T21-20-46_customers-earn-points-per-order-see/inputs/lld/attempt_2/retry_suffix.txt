FINDINGS:
  - - [critical] capabilityRecipes.widget-apply-redemption.steps[10].try[0]: "variables": {"basicCodeDiscount": "$discountInput"} — the binding references `$discountInput` but no prior step ever sets a binding named `discountInput`. The `discountCodeBasicCreate` mutation requires a fully-populated `DiscountCodeBasicInput` object (title, code, startsAt, customerGets, customerSelection, appliesOncePerCustomer, usageLimit). The compute steps build `discountCode`, `customerGid`, `startsAt`, and `discountValueDecimal` but never assemble them into a `discountInput` object. At runtime the codegen will emit `$discountInput` as undefined, causing the Shopify mutation to receive a null input and either throw or return userErrors, meaning no discount is ever created. Fix: Add a `compute` step before the `try_catch` that assembles the full `DiscountCodeBasicInput` object — e.g. `bindResultTo: "discountInput"`, `expression: "({ title: \`LOYALTY-${customerId}-${Date.now()}\`, code: discountCode, startsAt: startsAt, appliesOncePerCustomer: true, usageLimit: 1, customerGets: { items: { all: true }, value: { discountAmount: { amount: discountValueDecimal, appliesOnEachItem: false } } }, customerSelection: { customers: { add: [customerGid] } } })"` — then bind `basicCodeDiscount: "$discountInput"` in the mutation variables.
- [critical] capabilityRecipes.widget-cancel-redemption.steps[3].try[0]: "variables": {"id": "$redemptionInfo.discountGid"} — the `discountCodeDeactivate` mutation takes `id: ID!` which must be a Shopify GID, and `discountInfo.discountGid` is stored correctly. However, the `discountCodeDeactivate` op's `id` argument targets the `DiscountCodeNode` GID (`gid://shopify/DiscountCodeNode/…`), but the recipe stores the value from `discountCodeBasicCreate`'s `codeDiscountNode.id` (which is indeed a `DiscountCodeNode` GID) as `discount_external_id`. The binding variable name is `$redemptionInfo.discountGid` but `redemptionInfo` is declared as `({ pointsApplied: …, discountGid: claimedRedemption[0].discount_external_id, currency: … })` — the property is `discountGid`, and the variable key is `id`. This is structurally fine, but the `sql_claim` step (step index 1) marks the redemption `status = 'cancelled'` BEFORE the Shopify deactivate call. If the Shopify call fails, the catch arm records `failure_reason` but the redemption row is already `'cancelled'` — not `'active'`. The catch's `sql_update` writes `failure_reason` onto a row whose status is already `'cancelled'`, which is correct for audit, but on retry the `sql_claim` WHERE `status = 'active'` will find zero rows and return 404, making the failure unrecoverable without manual intervention. The status flip must happen AFTER the Shopify call succeeds, not before. Fix: Restructure the cancel recipe so the `sql_claim` only marks the row as an intermediate sentinel (e.g. `status = 'cancelling'`) or defer the status flip: keep the claim as a SELECT-for-update inside the `try` arm's `sql_transaction` after the Shopify deactivate succeeds — move the `UPDATE … SET status = 'cancelled'` into the `try` block's `sql_transaction` so a Shopify failure leaves the row still `'active'` and the customer can retry.
- [important] capabilityRecipes.widget-apply-redemption.steps[10].try[2] (sql_transaction inner sql_insert for point_ledger): "bindings": [{"name": "redemptionId", "source": "newRedemption[0].id"}, …] — `newRedemption` is the `bindResultTo` of the first `sql_insert` inside the same `sql_transaction`. Per the bind-scoping rules, `bindResultTo` set on a step inside `sql_transaction.steps` is visible only within that same transaction step list. The second `sql_insert` (ledger debit) references `newRedemption[0].id` from the first `sql_insert` inside the same transaction — this is a within-transaction forward reference which is consistent with the scoping rules and should work. However the `response` step at the end of the `try` block also references `$newRedemption[0].id`, and `newRedemption` is bound inside `sql_transaction.steps`, making it invisible outside the transaction per the spec: 'Inside `sql_transaction.steps` visible only within the transaction.' The codegen will not see `newRedemption` at the `response` step scope, producing an undefined reference. Fix: Add a `bindResultTo` on the `sql_transaction` step itself (e.g. `"bindResultTo": "txResult"`) and restructure so the `sql_transaction` returns the inserted redemption id, or hoist the `newRedemption` binding by splitting the first INSERT out of the transaction (insert redemption first at outer scope to get the id, then open the transaction for the ledger insert and snapshot update).
- [important] capabilityRecipes.reverse-points-on-refund.inputs: The `refunds/create` payload does not carry a `customer_id` field (confirmed by `payloadFields` — no `customer` or `customer_id` field is listed). The recipe correctly resolves the customer via `point_ledger` earn-entry lookup. However, the `refund_idempotency` INSERT at step 3 writes `customer_external_id = 0` as a placeholder (`VALUES (${refundId}, ${orderId}, 0, 0)`) and then a later `sql_update` patches it. This means that if the `sql_update` inside the transaction fails after the INSERT commits (impossible in a transaction, but the INSERT is NOT inside a `sql_transaction` — it is a standalone `sql_insert` at the top level), the `customer_external_id` column in `refund_idempotency` is left as `0`. More critically, the `sql_insert` claim fires BEFORE the `earnRows` lookup that establishes `earnInfo.customerId`, so on a refund for a pre-install order the claim row is inserted with `customer_external_id = 0` and `points_reversed = 0`, consuming the idempotency slot and preventing any future processing if the app is later backfilled with historical earn data. Fix: Move the `earnRows` sql_select and the skip-decision for missing earn entries to BEFORE the `refund_idempotency` INSERT claim, so the claim is only written when a valid earn entry exists; pass the resolved `earnInfo.customerId` directly into the INSERT rather than using a placeholder `0`.
- [minor] capabilityRecipes.widget-apply-redemption.edgeCases[1]: "Concurrent double-submit … the existing_redemption check is a SELECT not an atomic claim" — the plan itself acknowledges that the double-submit guard is a non-atomic SELECT, then argues the unique constraint on `(cart_external_id, customer_external_id, status)` saves it. However, that unique constraint allows multiple rows with `status = 'cancelled'` for the same `(cart, customer)` pair (only one `'active'` row is prevented because all three columns including `status` are in the constraint). More importantly, the Shopify `discountCodeBasicCreate` mutation fires BEFORE the INSERT that would hit the constraint, so two concurrent requests both pass the SELECT check, both call Shopify successfully creating two discount codes, and then one INSERT wins while the other fails — leaving one orphaned Shopify discount that was never recorded in the DB and whose points were never debited. The plan's edgeCase description mischaracterises this as safe. Fix: Add an atomic pre-claim step before the Shopify mutation: insert a 'pending' redemption row with ON CONFLICT (cart_external_id, customer_external_id, status) DO NOTHING RETURNING id, check claimed.length === 0 to exit early, then call Shopify, then update the row to 'active' with the returned discount GID — this ensures at most one Shopify call per cart per concurrent batch.
