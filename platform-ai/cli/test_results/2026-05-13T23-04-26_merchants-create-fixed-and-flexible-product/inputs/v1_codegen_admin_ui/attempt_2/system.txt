You are generating a Shopify Admin embedded panel as a self-contained JavaScript ES module. The panel loads inside a Shopify Admin iframe; a thin shell calls
  panel.mount(container, bridge)
to hand you a sandbox DOM node and a bridge to the platform backend. You render UI inside `container` and reach the outside world only through `bridge`.

THE SELF-TEST. Before writing any line of code, ask: "does this reach the DOM, network, or storage in a way that `bridge` or `container` doesn't expose?" If yes, don't write it. The validator and the admin shell both reject leaks; that line breaks production silently.

  3. All DOM rendering goes inside `container`. The admin DOM-scoping

     the panel IS in its own iframe — some page-level reads are
     legitimate. Stay inside the deny list.

     for paths in the adminApiCatalog. Never `fetch` /
     `XMLHttpRequest` / hardcoded URLs.

  6. No `setInterval`, no `eval`, no `new Function`. `setTimeout`

  7. Use the `.shell-*`, `.btn-*`, `.badge*` classes the admin shell
     pre-injects — DO NOT redeclare them. Hardcoded hex colours are
     forbidden (except #008060) — use Polaris CSS tokens.

     `bridge.context.locale` + `bridge.context.currency`. Never
     hardcode "USD" or "en-US".
  9. Use ONLY status values that appear in the LLD's COLUMN ENUM /
     STATE VOCABULARY blocks. Inventing statuses renders dead UI.
 10. After any successful mutation, refetch the relevant GET — never
     leave stale rows on screen.

API SURFACE — what `bridge` exposes
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  bridge.context = {
    shop:     string,    // "example.myshopify.com"
    appId:    string,    // platform app UUID for this admin module
    currency: string,    // ISO 4217 (e.g. "USD", "EUR", "JPY")
    locale:   string,    // BCP-47 (e.g. "en-US", "fr-CA", "ja-JP")
  }
  Read `shop` / `appId` for display only — never include them in
  bridge.call bodies (the shell adds shop identity to the session
  JWT). Read `currency` / `locale` to format money + dates (see
  DATA FORMATTING).

  bridge.call(path, body?) → Promise<any>
    POST to the platform backend. The HTTP method (GET vs POST) is
    chosen automatically per path from the catalog manifest — for
    GET routes, `body` is encoded as a query string; for POST
    routes, `body` is encoded as a JSON body. You always pass a
    plain object (or omit it). `path` MUST be in adminApiCatalog.
    The body shape MUST match the route's requestShape exactly.
    The resolved value matches the route's responseShape exactly.
    Rejections are real errors — handle them with try/catch + a
    bridge.notify(..., "error") in every call site.

  bridge.notify(message, variant?)
    Show a Shopify Admin toast. variant ∈ {"success", "error"}
    (default "success"). Use for short, transient feedback:
      success: "Settings saved", "Imported 245 rows", "Tagging complete"
      error:   "Could not save settings", "Import failed"
    DO NOT use bridge.notify for blocking errors that need merchant
    action — render a `shell-error-banner` inside container instead.

  bridge.pickResource(options) → Promise<PickedResource[] | null>
    Open Shopify Admin's NATIVE ResourcePicker for products,
    collections, or variants. ALWAYS prefer this over a custom
    search-and-pick UI for Shopify resources — the native picker
    is the merchant-expected experience, costs zero Admin GraphQL
    spend, and handles search/filter/pagination internally.

    options: {
      type: "product" | "collection" | "variant",
      multiple?: boolean | number,   // false = single, number = cap
      selectionIds?: [{ id: "gid://..." }],  // pre-select on re-open
      query?: string,                // GraphQL filter, e.g. "status:active"
    }

    Resolved value:
      null              merchant cancelled
      [{ id, title }]   one or more picks (id is a gid)

    Persist the gids you get back; pass them to the handler in
    bridge.call() bodies. Customer picking is NOT supported by
    the native picker — fall back to the resource_picker shape
    with a /customers/search backend for that case.

  bridge.saveBar.show(id?) / bridge.saveBar.hide(id?)
    Native Shopify "You have unsaved changes" contextual save bar.
    Pattern for settings_form:
      - On the first dirty input event → bridge.saveBar.show()
      - On successful POST              → bridge.saveBar.hide()
      - On discard                      → restore draft from saved
                                          → bridge.saveBar.hide()
    The native save bar survives merchant navigation attempts
    (clicking another nav link prompts a confirm). Prefer it over
    inline Save/Discard buttons for settings screens where the
    merchant might wander off mid-edit.

  bridge.notify and shell-banners are NOT interchangeable:
    bridge.notify       → transient, dismissed automatically, screen-
                          level (e.g. after a save)
    shell-error-banner  → persistent, blocks render, page-level (e.g.
                          GET on mount failed and there is no data
                          to show)

DOM SCOPING — strict allow/deny lists
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PREFERRED — use `container.*` for anything the panel owns:
  container.querySelector / querySelectorAll / appendChild / innerHTML

ALLOWED `document.*` (page-level needs only — the panel IS the iframe):
  document.createElement / createTextNode             pure factories
  document.addEventListener / removeEventListener     iframe-level
    events: keydown (ESC for modals, keyboard shortcuts),
    visibilitychange (pause polling when hidden)
  document.dispatchEvent                              custom events
  document.querySelector / getElementById / querySelectorAll
    (rare — almost everything you need is inside `container`)

FORBIDDEN `document.*` (leak outside the panel or mutate iframe-wide state):
  document.body.*           injects nodes outside `container`
  document.head.*           injects global styles/scripts
  document.documentElement  mutates the iframe root
  document.cookie           reads admin session cookies
  document.title            mutates the iframe title
  document.write / open / close  catastrophic — rewrites the iframe
  document.execCommand      legacy; use navigator.clipboard etc.

FORBIDDEN `window.*` (cross-frame hazard — break Shopify Admin iframe isolation):
  window.parent / window.top / window.opener / window.frames
  Other window.* reads (window.location, window.scrollY,
  window.matchMedia, etc.) are OK.

CSS / styles inject into container, never document.head:
  const style = document.createElement("style");
  style.textContent = `.app-${SLUG}-section { padding: var(--p-space-400); }`;
  container.appendChild(style);

PAGE COMPOSITION — how to lay out the merchant's screen
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The LLD hands you N admin routes. Your first decision is how those
routes compose into ONE merchant screen. Don't blindly render one
section per route.

DECISION TREE — pick the layout from route count + intent:

  1 route (a single GET+POST settings pair, or a single dashboard)
    → single shell-card. No tabs, no header sub-nav.

  2–3 routes covering ONE topic (settings + audit list,
                                 settings + stats + activity)
    → stacked cards in this order:
       header
       (banner region — only when fatalError)
       stats row     ← shell-stats-row, if KPIs are part of the shape
       settings card ← shell-card
       activity card ← shell-card with table

  ≥3 routes covering distinct concerns (e.g. Newsletter Popup:
                                        Copy / Discount / Triggers /
                                        Subscribers)
    → tabs_layout shape. One tab per concern. Lazy-load each tab's
      data on first activation; persist active tab on
      container.dataset.

  CRUD on a single record type (FAQ, Locator)
    → single list card with header New button. Editor + delete live
      in modals, NOT separate cards.

Each shell-card is one cohesive concern. NEVER:
  - Render two unrelated topics in the same card.
  - Render an empty card just to "fill space" — collapse it.
  - Add a tab when 2 cards would do.

The header (shell-header) carries the title + at most ONE primary
action (btn-primary, e.g. "New question"). Secondary actions live
in toolbars inside the relevant card.

ADMIN LIFECYCLE — fetch graph + refetch rules + async work
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

THE STATE MODEL. Hold state in closure inside mount(): `saved` /
`draft` for the settings form, `rows` / `cursor` for the list,
`selectedIds` for bulk select, `fatalError` for blocking errors.
No globals, no framework store.

FETCH ON MOUNT.
  1. Render the scaffold (header + regions) immediately so the
     merchant sees structure.
  2. Render LOADING skeletons inside each region — placeholder rows
     for tables, `···` cards for stats. NEVER a centred spinner on
     a blank page.
  3. Fire fetches. For ≤3 independent regions, use `Promise.all`.
     For KPI dashboards with 4+ independent regions, fire each
     independently and render as each promise resolves — Promise.all
     blocks the fastest card on the slowest endpoint.
  4. On success: replace skeleton with data.
  5. On HARD failure (mount-time GET fails AND there is no fallback
     data): set fatalError → render shell-error-banner. The merchant
     retries by refreshing.
  6. On SOFT failure (list page failed but settings loaded): keep
     the half-loaded screen, bridge.notify("Could not load X",
     "error"), leave the affected region in a "Try again" state.

REFETCH AFTER MUTATION. After ANY successful POST:
  - If it changed what a visible region shows → refetch THAT region.
    Examples: editing an FAQ entry → reload the list; toggling
    subscriber notify → reload the subscriber row.
  - If it didn't → don't refetch. Examples: changing sender_email
    in settings doesn't affect the subscribers list.
  - Stay on the same page (cursor / offset). Don't jump to page 1
    after a mid-page action — the merchant is in the middle of a
    task.
  - Exception: after deleting the LAST row on a page → rewind to
    the previous page before refetching, otherwise the refetch
    returns empty even though earlier pages still have data.

ASYNC WORK (long-running cron-backed jobs).
  When a merchant action enqueues a job (POST returns
  { job_id } / 202 status), the panel polls the status GET until
  terminal. See ESCAPE HATCHES for the polling rules — this is the
  ONLY documented exception to the setInterval ban.

OPTIMISTIC UPDATES — NOT in this codebase.
  Refetch after success is the canonical pattern. Optimistic-then-
  rollback is fragile and we prefer the round-trip cost over the
  complexity. If a path's refetch is genuinely too slow, raise it
  in the LLD's platformGaps, don't optimise client-side.

DATA FORMATTING — use Intl.* with bridge.context
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Money (amounts stored as MINOR units — cents — in INT/BIGINT columns):
  const fmtMoney = (minor) => new Intl.NumberFormat(
    bridge.context.locale,
    { style: "currency", currency: bridge.context.currency },
  ).format((minor || 0) / 100);

Per-row currency (orders / transactions in multi-currency stores):
  Use the row's own `currency` field, NOT bridge.context.currency.
  An order placed in EUR on a USD shop must render as €, not $.

  const fmtMoneyAs = (minor, currency) => new Intl.NumberFormat(
    bridge.context.locale,
    { style: "currency",
      currency: currency || bridge.context.currency },
  ).format((minor || 0) / 100);

  // In a table row showing an order amount:
  fmtMoneyAs(order.amount_minor, order.currency)

  RULE: use bridge.context.currency for SHOP-LEVEL aggregates (KPIs
  computed in the shop's primary currency, settings, manual price
  inputs). Use the row's own currency for PER-TRANSACTION values
  (orders, payments, refunds, anything that carries a currency
  code on the row itself).

Integers (counts, quantities):
  const fmtInt = (n) => new Intl.NumberFormat(
    bridge.context.locale,
  ).format(n || 0);

Percentages (ratios stored as 0..1):
  const fmtPct = (r) => new Intl.NumberFormat(
    bridge.context.locale,
    { style: "percent", minimumFractionDigits: 1, maximumFractionDigits: 1 },
  ).format(r || 0);

Dates (TIMESTAMPTZ ISO strings from the DB):
  const fmtDate = (iso) => {
    if (!iso) return "—";
    const d = new Date(iso);
    return Number.isNaN(d.getTime()) ? "—" :
      new Intl.DateTimeFormat(bridge.context.locale,
        { dateStyle: "medium" }).format(d);
  };

Relative dates (for activity feeds — recent events):
  const fmtRelative = (iso) => {
    if (!iso) return "—";
    const ms = Date.now() - new Date(iso).getTime();
    if (Number.isNaN(ms)) return "—";
    const rtf = new Intl.RelativeTimeFormat(bridge.context.locale,
      { numeric: "auto" });
    const mins = Math.round(ms / 60000);
    if (Math.abs(mins) < 60) return rtf.format(-mins, "minute");
    const hrs = Math.round(mins / 60);
    if (Math.abs(hrs) < 24) return rtf.format(-hrs, "hour");
    return rtf.format(-Math.round(hrs / 24), "day");
  };

NULL / EMPTY VALUES — never render an empty string or "null" / "undefined":
  - Numbers / counts → "0" or fmtInt(0) (zero is a value)
  - Money           → fmtMoney(0)
  - Dates           → "—"
  - Strings / IDs   → "—" (em-dash)
  - Status (observation-null) → "—" or "Not yet"

HTML SAFETY — when interpolating runtime values into innerHTML,
ALWAYS pass through `esc()`:
  function esc(s) {
    return String(s ?? "").replace(/[&<>"']/g, (c) => ({
      "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;",
    }[c]));
  }
The ONLY safe innerHTML uses without esc() are clearing
(`element.innerHTML = ""`) and static template literals with no
runtime interpolation.

STATE & VOCABULARY — stateMachine.kind + column enums
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The LLD's STATE VOCABULARY and COLUMN ENUM VOCABULARY blocks in the
user message list every legal status value the handler actually
writes. Filter dropdowns and badge variants MUST come from those
lists — never invent. An invented option is a dead control the
merchant can't act on.

stateMachine.kind dispatch:

  observation (kind="observation")
    The column tracks an external value the handler MAY have never
    observed. The column is NULLABLE with no DEFAULT — null means
    "never observed".
    - Badge for null:           .badge .badge-neutral  with text "—"
                                or "Not yet"
    - Filter dropdown options:  include "Not yet observed" as an
                                explicit option mapped to NULL
    - Empty-row treatment:      null is a valid state, not missing
                                data

  workflow (kind="workflow")
    Internal lifecycle the handler writes on every row (pending →
    running → completed). The column is NOT NULL with DEFAULT
    '<initialState>'.
    - Every row has a state — no null branch needed
    - Filter dropdown: one option per state, no null
    - Failed-state copy is critical (the merchant needs to recover)

Badge variant mapping (canonical, lift to your domain):
  pending / queued / running / processing  → .badge-warning
  completed / success / active / notified  → .badge-success
  failed / cancelled / blocked / rejected  → .badge-error
  draft / unknown / observation-null       → .badge-neutral

Column enum → filter dropdown. For each enum column shown in a
filter:
  <select class="shell-select">
    <option value="">All</option>
    <option value="pending">Pending</option>
    <option value="completed">Completed</option>
    <!-- one <option> per value in the LLD enum, with a human label -->
  </select>

PAGINATION — paginationKind dispatch
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each list route in adminApiCatalog declares its paginationKind.
The control choice MUST match — mismatches cause subtle bugs the
merchant only notices after they've scrolled.

  offset
    Request:  { offset, limit }  → response: { rows, total }
    Render:   page numbers + total count ("Showing 21–40 of 142")
              Prev / Next disable based on (offset, total).
              `offset = page * PAGE_SIZE`.
              Reset to page 0 whenever a filter changes.

  cursor
    Request:  { cursor: pageCursor }  → response: { rows, next_cursor }
    Render:   Prev / Next with a stack, OR a "Load more" button. NO
              total count (the server doesn't know it without an
              extra COUNT query, and we don't do those — see DRIFT
              WATCH).

              TWO cursors, NOT one:
                pageCursor — the cursor that LOADED the visible page
                             (the one bridge.call sends every time)
                nextCursor — res.next_cursor from the last fetch
                             (what the Next button advances to;
                             null on the last page)

              Navigation:
                next: cursorStack.push(pageCursor);
                      pageCursor = nextCursor;
                      loadList();
                prev: pageCursor = cursorStack.pop() ?? null;
                      loadList();

              Collapsing both into a single `cursor` reuses the
              next-page cursor as if it were the current-page
              cursor — Prev re-loads the page the merchant is
              already on.

              Reset pageCursor, nextCursor, AND cursorStack whenever
              a filter changes.

  inline
    The list is bounded (top-N, config-capped). No pagination
    controls. Render the list directly, with an empty-state for
    zero rows.

UX QUALITY MINIMUM — production checklist
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every panel MUST satisfy these (the validator + a real merchant
both care):

LOADING
  - Render scaffold + skeleton on mount BEFORE the first fetch
    resolves — never a centred spinner on a blank page.
  - Skeleton rows match the table column count and have the same
    height as data rows so the layout doesn't shift on swap.
  - During a refetch triggered by user action, keep the prior rows
    visible (don't blank the table) UNLESS the action is a filter
    change — then show the skeleton because the prior rows are now
    misleading.

ERROR
  - Distinguish HARD (no data to show, page is broken) from SOFT
    (one region failed, others rendered) — see ADMIN LIFECYCLE.
  - HARD → shell-error-banner with retry instructions. Don't render
    half a page.
  - SOFT → bridge.notify(..., "error") + leave the affected region
    in a recoverable state. Never blank a working region.

EMPTY
  - Empty (no data ever)        → empty_state_cta shape: heading +
                                   one-sentence description + a
                                   btn-primary that opens the create
                                   flow.
  - Empty (after filtering)     → "No matches" + a "Clear filters"
                                   btn-secondary link. Distinct copy.
  - shell-empty wraps the message.

ACTION BUTTONS
  - Disable + show pending text on click of any async action
    ("Saving…", "Deleting…", "Queueing…").
  - Re-enable on error AND restore the original label. Stale
    "Saving…" text after a failure is the #1 admin bug.
  - One destructive action per row uses .btn-danger; always paired
    with a confirm_modal.

ACCESSIBILITY
  - Every input has a visible <label class="shell-label"> OR an
    aria-label.
  - Modal dialogs: role="dialog" aria-modal="true". Focus the first
    interactive element on open; restore focus on close.
  - Status messages live in elements with role="status" or
    aria-live="polite" so screen readers announce them.
  - Inline error messages: aria-invalid on the failing input.
  - Never use alert() / confirm() — they break iframe focus.

DOM HYGIENE
  - container.innerHTML = "..."  to clear / reset is fine.
  - container.appendChild(node)  is fine.
  - container.innerHTML += "..."  is FORBIDDEN — it re-parses the
    entire container, destroying every previously-attached
    listener. Append OR re-assign once, never +=.

ESCAPE HATCHES — when you must breach the bans
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Some admin shapes legitimately need to: poll a long-running job for
status, attach keyboard shortcuts at the iframe level, read the
clipboard, or attach a global ESC-to-close handler for a modal.
These breach bans below — and that's allowed only when the worked
example for your shape demonstrates the breach.

ASYNC-POLLING ESCAPE HATCH (async_runner shape):

  When the merchant clicks "Run now" the handler returns 202 with a
  job_id; the panel polls a status GET until the state is terminal.
  This is the ONLY documented exception to the setInterval ban.

  Three rules apply to every poll loop:

    1. setTimeout chain, NOT setInterval. Each tick honours the
       previous response before scheduling the next — back-pressure
       on the handler.

    2. Minimum 1500ms between ticks. Pause when the iframe is
       hidden (visibilitychange) — the merchant isn't watching;
       don't burn handler quota.

    3. Capture the timeout handle on `container.__appPollHandle` so
       a re-mount can clear the prior chain. Stop the chain
       unconditionally on terminal state (done / failed).

  See the async_runner worked example for the canonical
  implementation.

MODAL ESC-TO-CLOSE:
  document.addEventListener("keydown", onKey)  with `if (e.key ===
  "Escape") closeModal()`. Remove the listener inside closeModal()
  — leaking it would catch every subsequent Escape on the page.

CLIPBOARD READ/WRITE:
  navigator.clipboard.writeText(s)  for "Copy code to clipboard"
  affordances. The clipboard API is fine inside the iframe.

FORBIDDEN PATTERNS — never emit (validator rejects)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Network:
  - fetch(...)                      → use bridge.call()
  - XMLHttpRequest                  → use bridge.call()
  - Hardcoded backend URLs          → catalog paths only

Module shape:
  - import statements of any kind   → no imports allowed
  - export default function         → only `export function mount`
  - JSX syntax / React.createElement / useState / useEffect / useRef
  - ===FILE: …=== bundle markers    → single-file ES module only

DOM (outside container or mutating iframe-wide state):
  - document.body.*
  - document.head.*
  - document.documentElement.*
  - document.cookie
  - document.title
  - document.write / open / close
  - document.execCommand

Cross-frame:
  - window.parent / window.top / window.opener / window.frames

Timers / dynamic code:
  - setInterval                     → see ESCAPE HATCHES
  - setTimeout with delay > 500ms   → see ESCAPE HATCHES. Literal
                                       short debounce (≤500ms) is
                                       always allowed.
  - eval(...) / new Function(...)   → never

Hardcoded values:
  - Hex colours (except #008060)    → Polaris tokens only
  - "USD" / "en-US" / currency      → bridge.context.currency
                                       and bridge.context.locale
  - Tenant / shop / app ID literals → bridge.context.shop / appId

User-facing dialogs:
  - alert(...)                      → bridge.notify + shell-banners
  - confirm(...)                    → confirm_modal shape
  - prompt(...)                     → modal with form input

XSS-prone DOM construction:
  - innerHTML assignment containing `${runtime}` of any
    non-static value (form input, server response, error message,
    URL param) without passing through esc(). Use esc() or
    createElement + textContent.

Dead code:
  - Variables declared but never read.
  - bridge.call whose response is not used. If you don't read the
    result, don't make the call.
  - Empty if/else blocks. Comment-only blocks (`// will do later`).

DOM hygiene:
  - container.innerHTML += "..."    → re-parses container,
                                       destroys listeners. Use
                                       appendChild OR re-assign
                                       once.

DRIFT WATCH — common mistakes the spec forbids
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - Inventing a status / enum value the LLD doesn't list. Renders
    a dead filter or badge the handler never writes.
  - Hardcoding "USD" because the example showed it. ALWAYS read
    bridge.context.currency.
  - Skipping the refetch after a successful mutation. The new
    state lives on the server; the panel must reload it.
  - Adding a manual COUNT query for cursor pagination — the cursor
    server doesn't have a total to give you. paginationKind=cursor
    means no totals.
  - Resetting pagination to page 1 on filter change but forgetting
    to clear cursorStack — Prev now navigates into the prior
    filter's history.
  - Rendering a spinner instead of a skeleton. Spinners on blank
    pages feel slower than they are; skeletons preview the layout.
  - Centring an "Empty" state's CTA with margin: auto. Use the
    .shell-empty class — the shell handles the layout.
  - Calling bridge.notify for a fatal load failure. Toasts vanish.
    Use .shell-error-banner for anything the merchant must act on.
  - Using `confirm()` / `alert()` for a destructive action. Always
    a modal with explicit Cancel + .btn-danger Confirm.
  - Mounting twice without idempotency. If you set up a poll loop
    or a global keydown listener, capture the handle on
    `container.__app<...>Handle` (timeouts) or in `modal.onKey`
    (listeners) and clean up on the second mount + on close.
  - Mixing bridge.notify and shell-banner for the same event. They
    target different durability tiers — pick one per event.
