REVIEWER FINDINGS — apply each finding's fix to the relevant section of
the prior plan; leave everything else untouched.

- [important] externalContracts[0] (GET /admin/dashboard): X2: The responseShape for GET /admin/dashboard declares `"top_products": "list"` but the route exposes no `limit`, `cursor`, or `page` parameter in its requestShape — only `date_range_start` and `date_range_end`. The top-products list length is controlled by the merchant's saved setting (default top_products_limit) but there is no way for the caller to override it at request time, and no pagination cursor is present, making the list endpoint unusable if the merchant wants to explore beyond the stored default or if the default is large. Fix: Add `top_products_limit` (kind: count) to the requestShape of GET /admin/dashboard as an optional override, or add a cursor/page parameter and document the maximum page size, so the list surface is fully navigable.
- [important] capabilities[4] (record-snapshot-run-outcome) / persistence[3] (snapshot_run_log): C3: The capability `record-snapshot-run-outcome` is described as recording whether the job completed or failed, meaning the capability itself assigns the outcome value — yet `"dataNeeds": ["run identifier", "outcome", "orders processed count", "failure reason"]` lists `outcome` as a dataNeed. Because the snapshot job is the only actor that calls this capability and it supplies the outcome value directly (success or failure), `outcome` is a caller-supplied field and is correctly present; however `run identifier` is a server-side identifier generated when the run row is first inserted (per `snapshot_run_log.id` keyed by `started_at`). The LLD has no signal about whether the capability creates a new row (INSERT) or closes an existing in-progress row (UPDATE) — these are two distinct write paths and bundling both into one capability conflates an initial-state insert with a terminal-state update, hiding the in-progress → completed/failed transition that the concurrent-run edge case depends on. Fix: Split into two capabilities: `open-snapshot-run` (INSERT a row with status=in_progress, dataNeeds: started_at) and `close-snapshot-run` (UPDATE the row to completed or failed, dataNeeds: run identifier, outcome, orders processed count, failure reason) so the LLD can generate the correct INSERT vs UPDATE paths and the concurrency guard has a clear in-progress row to detect.
- [important] dataFlow: D1: The dataFlow narrative describes the scheduled job bulk-fetching orders and upserting snapshot rows, then describes the dashboard read path, but never mentions what happens after `record-snapshot-run-outcome` writes a failure — there is no description of alerting, retry scheduling, or even that the merchant can observe the failure through the dashboard. The edgeCase covering mid-run failure says 'the next run reprocesses all days' but the dataFlow gives the LLD no signal about how failure surfaces to the operator, leaving the failure-path requirements entirely implicit. Fix: Extend the dataFlow narrative with a sentence describing what happens on job failure: e.g. the snapshot_run_log row is written with status=failed and failure_reason, and the admin dashboard's data-freshness indicator reads the most recent snapshot_run_log row to surface staleness — giving the LLD a concrete end-to-end path for the failure branch.
- [minor] capabilities[5] (compute-dashboard-metrics): C5: The capability `compute-dashboard-metrics` has `"returnsList": false` but its description states it produces `"top products ranked by revenue"` — a ranked list of products that the merchant browses. Top-products is a list result that the LLD would need to paginate or limit, yet returnsList=false signals to the LLD that no list-handling helper contract is needed, which conflicts with the top_products list in the GET /admin/dashboard responseShape. Fix: Set `returnsList: true` on `compute-dashboard-metrics` so the LLD applies the correct list-handling and limiting logic for the top-products output.
