REVIEWER FINDINGS — apply each finding's fix to the relevant section of
the prior plan; leave everything else untouched.

- [important] externalContracts[0] (GET /widget/questions): X2: The GET /widget/questions route has `"questions": "list"` in its responseShape but exposes no `count` and no cursor or page parameter in its requestShape. The capability 'list-published-questions' description says 'Return all published questions and answers for a product' with no pagination guard, meaning a product with hundreds of Q&A entries forces the widget to download the full set on every page load, which is unusable at scale and contradicts the qualityBrief's 'without overwhelming the product page' requirement. Fix: Add a `limit` (count) and `cursor` (text) parameter to the requestShape, and add `next_cursor` (text) and `total_count` (count) to the responseShape; update the 'list-published-questions' capability's dataNeeds to include 'page cursor' and 'limit' accordingly.
- [important] capabilities[2] (record-answer) and capabilities[3] (update-question-status): C4b: Both 'record-answer' and 'update-question-status' are triggered by the same actor (the merchant via admin UI) and write to the same lifecycle column (`status` on `product_questions`). 'record-answer' transitions to `answered` and 'update-question-status' transitions to `published`, `unpublished`, or `rejected` — all terminal or re-entrant states on the same column driven by the same surface. Having two separate capabilities for these transitions creates a race risk: a merchant could call `update-question-status` with `published` concurrently with `record-answer`, allowing a partially-answered question to reach `published` status without the answered-gate check if the two capabilities execute independently with no shared transaction boundary, which the LLD has no signal to prevent. Fix: Merge 'record-answer' and 'update-question-status' into a single 'answer-and-publish-question' capability with `dataNeeds: [question id, answer text, target status]`, enforcing the answered-before-published rule atomically inside one write path; or, if kept separate, add an explicit edge case stating that `update-question-status` must acquire a row-level lock and re-validate the `answer_text IS NOT NULL` constraint before allowing `published`.
- [important] edgeCases: E1: The plan includes a notify surface implied by the qualityBrief's explicit mention of 'avoid email notifications unless explicitly requested' — confirming the plan's authors considered and excluded notifications — but the 'record-answer' and 'update-question-status' capabilities have no edge case covering what happens if the status-write itself partially fails (e.g. DB write succeeds but the response to the admin client is lost), leaving the merchant's UI out of sync with the stored state. More critically, there is no edge case for the concurrent-write scenario on `record-answer` specifically: if two merchants submit an answer for the same question simultaneously, the last write wins but no locking or conflict-detection signal is given to the LLD. The existing concurrency edge case covers `update-question-status` only (`"Two admin users concurrently update the status"`), leaving `record-answer` unguarded. Fix: Add an edge case: 'Two merchants concurrently submit answers for the same question — the last write wins; the response must return the persisted answer text and status so the losing client's UI is corrected without a page reload.'
- [minor] persistence[0].queryPatterns: P1: The queryPatterns entry `"single question looked up by id when recording an answer or updating status"` implies a point-lookup by `id`, but no column in `product_questions` is explicitly marked with a unique index or primary-key role beyond the generic `"role": "identifier"` declaration. The LLD must know whether `id` is the primary key (index implied) or a secondary unique column requiring an explicit UNIQUE index; without this, the generated DDL may omit the index and make point-lookups a full-table scan. Fix: Set `keyedBy` to explicitly state 'primary key on id column' (or rename to clarify it is the surrogate primary key), so the LLD generates the correct DDL constraint and index without guessing.
