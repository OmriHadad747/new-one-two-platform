Fix: Add `"conversion_attribution_window_days": "count"` to the PUT `/admin/settings` requestShape so the field is supplied by the merchant and the capability's dataNeed is reachable.
- [important] capabilities[send-restock-notification-email] / capabilities[record-send-outcome]: `send-restock-notification-email` has `usesWorkflow: true` but its description is "Send a restock notification email to a single subscriber" — it dispatches an email and does not own a status lifecycle. Conversely, `record-send-outcome` has `usesWorkflow: false` but its description is "Mark a notification_send as sent or failed and increment the batch emails_sent counter" — it is the explicit status-transition owner for `notification_sends`. The `usesWorkflow` flag is the only signal telling the coding agent to import the atomic workflow helper instead of hand-rolling a claim/update loop; having it on the wrong capability will cause the outcome-recording path to be implemented without the helper's atomicity guarantees. Fix: Set `usesWorkflow: false` on `send-restock-notification-email` and `usesWorkflow: true` on `record-send-outcome`, which is the capability that actually writes `notification_sends` status transitions.
- [important] externalContracts[GET /unsubscribe] / capabilities[send-restock-notification-email] / dataFlow: The plan promises "quiet hours so nothing sends late at night" — `save-settings` persists `quiet_hours_start` and `quiet_hours_end`, and `read-settings` exposes them — but no capability in the notification pipeline checks or enforces the quiet window, and there is no schedule trigger to resume a deferred batch once the quiet period ends. A restock webhook that fires at 2 AM will either dispatch emails immediately (violating quiet hours) or have no mechanism to delay and retry after the window opens. The promise has no realizer. Fix: Add a schedule trigger (e.g. "every 15 minutes") whose `perTickWork` is "dispatch any notification_sends that are pending and whose batch was created during quiet hours, now that the quiet window has passed", and add `"quiet hours start"` and `"quiet hours end"` to `select-and-open-notification-batch`'s dataNeeds so it can gate batch dispatch against the configured window.
- [minor] capabilities[refresh-demand-stats-snapshot].dataNeeds / capabilities[refresh-demand-stats-snapshot].shopifySteps[0]: The capability always requires `"variant external id"` as a dataNeed and resolves it through the `productVariant` op, but for product-level signups (`item_type = product`) there is no variant — `item_external_id` is a product id and no variant id is available from the restock event or the conversion event that triggers a refresh. The coding agent has no described fallback for this case, so snapshot refreshes for product-level items will either error or silently skip the title denormalization. Fix: Make `"variant external id"` nullable in the dataNeeds description and document a fallback in the shopifyStep (e.g. "when item_type is product, use the `product` query instead to fetch product title, omitting variant_title") so the coding agent handles both item types.
