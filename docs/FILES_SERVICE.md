# Files Service — Integration Plan

`POST /services/files/upload`

Handlers generate files in memory (PDF via pdfkit, CSV via csv-stringify, Excel via
exceljs, images via sharp — all pre-installed in the handler template) and call this
endpoint to persist them. The platform stores the file in GCS and returns a signed URL
the handler can drop into an email, an admin-UI download link, or a Shopify metafield.

---

## Architecture decision — shared bucket, per-tenant prefix

Every generated file lands in a single private bucket:

```
new-one-two-files-{PROJECT_ID}
  └── {tenantId}/
        └── {appId}/
              └── {fileId}          ← GCS object key (UUID, no extension)
                    metadata:
                      x-goog-meta-filename:     "invoice-1234.pdf"
                      x-goog-meta-content-type: "application/pdf"
                      x-goog-meta-app-id:       "<uuid>"
                      x-goog-meta-tenant-id:    "<uuid>"
```

**Why not per-tenant buckets:**
- GCS bucket creation adds ~2 s of latency to OAuth install — bad UX
- Soft limit of ~1 M buckets per project is fine in theory but adds toil at scale
- IAM isolation is not needed: access is exclusively through platform-issued signed
  URLs, never direct. Tenants never touch the bucket themselves.
- A single lifecycle rule on the bucket handles TTL for everyone.

**Why a separate bucket (not reusing `new-one-two-bundles-{PROJECT_ID}`):**
- Bundles are public (`allUsers: objectViewer`). Files are private. Mixing them on one
  bucket means either the files bucket gets accidentally public or the bundles bucket
  loses its CDN-friendly public policy.
- Separate lifecycle rules: bundles are permanent; files expire after 90 days.

## GCS infrastructure

### New bucket

```bash
gcloud storage buckets create gs://new-one-two-files-$PROJECT_ID \
  --location=$REGION \
  --uniform-bucket-level-access \
  --no-public-access-prevention   # default is fine; no allUsers binding added
```

No public IAM binding. `api-sa` already has `roles/storage.objectAdmin` project-wide
(see GCP_DEPLOYMENT.md → Service Accounts) — no new IAM grant needed.

### Lifecycle rule (90-day TTL)

```bash
cat > /tmp/files-lifecycle.json << 'EOF'
{
  "rule": [{
    "action": { "type": "Delete" },
    "condition": { "age": 90 }
  }]
}
EOF
gcloud storage buckets update gs://new-one-two-files-$PROJECT_ID \
  --lifecycle-file=/tmp/files-lifecycle.json
```

### Local dev (docker-compose)

Add to the `gcs-init` `entrypoint` in `docker-compose.yml`:

```sh
curl -s -X POST 'http://fake-gcs:4443/storage/v1/b?project=new-one-two-dev' \
  -H 'Content-Type: application/json' \
  -d '{"name":"new-one-two-files-dev"}' && echo "Files bucket created"
```

And add `GCS_FILES_BUCKET=new-one-two-files-dev` to `.env` / `.env.local`.

## API endpoint

### Request

```
POST /services/files/upload
Authorization: Bearer <Google OIDC ID token>   (handler's Cloud Run SA)
Content-Type: application/json

{
  "filename":        "invoice-1234.pdf",   // used in Content-Disposition; 1–255 chars
  "contentType":     "application/pdf",    // must be in the allowlist (see below)
  "data":            "<base64>",           // raw file bytes, base64-encoded; max 10 MB decoded
  "expiresInSeconds": 3600                 // optional; default 3600, max 86400 (24 h)
}
```

### Responses

| Status | Body | When |
|--------|------|------|
| 200 | `{ ok: true, fileId, url, expiresAt }` | Upload succeeded; `url` is a GCS V4 signed URL |
| 400 | `{ error: "invalid_content_type" \| "file_too_large" \| "invalid_base64" \| ... }` | Caller bug |
| 429 | `{ error: "quota_exceeded", limit, current, resetsAt }` | Monthly storage quota hit |
| 401/403 | — | Auth failure |
| 5xx | `{ error: "upload_failed" }` | GCS transient error |

### Content-type allowlist

```
application/pdf
text/csv
text/plain
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet   (xlsx)
application/zip
image/png
image/jpeg
image/gif
image/webp
```

Anything else → `400 { error: "invalid_content_type" }`.

### Size limit

Decoded file size > 10 MB → `400 { error: "file_too_large", maxBytes: 10485760 }`.
Enforced server-side after base64-decode, before GCS write.

### fileId

A UUID v4 generated by the platform. Used as the GCS object key. The `filename` and
`contentType` are stored as object metadata so the signed URL serves the right
`Content-Disposition` and `Content-Type` headers.

## Handler SDK

Add to `platform-back/templates/handler/src/lib/platform.ts`:

```ts
export interface FilesUploadInput {
  filename: string;
  contentType: string;
  data: string;            // base64
  expiresInSeconds?: number;
}

export type FilesUploadResult = {
  ok: true;
  fileId: string;
  url: string;
  expiresAt: string;       // ISO-8601
};

// platform.files.upload(input) — throws QuotaExceeded on 429
export const platform = {
  email: { ... },
  files: { upload: filesUpload },
  QuotaExceeded,
};
```

Same response taxonomy as email: returns `FilesUploadResult` on 200, throws
`QuotaExceeded` on 429, throws `Error` on 4xx/5xx.

## Lifecycle & edge cases

### Uninstall cleanup

When a tenant uninstalls the Shopify app, the deployer's uninstall flow must:

1. Delete all GCS objects under prefix `{tenantId}/`:
   ```ts
   const [files] = await storage.bucket(FILES_BUCKET).getFiles({
     prefix: `${tenantId}/`,
   });
   await Promise.all(files.map(f => f.delete()));
   ```
2. This runs in the existing `uninstallApp` deployer step, after the Cloud Run service
   is deleted and before the DB schema is dropped.

### App deletion (without full uninstall)

Same as above but prefix `{tenantId}/{appId}/`.

### Signed URL expiry vs object lifetime

Signed URLs expire (default 1 h). Objects live for 90 days (lifecycle rule). This is
intentional: the URL becomes invalid long before the object is deleted, which protects
against stale links being shared. If a handler needs a longer-lived link it can request
up to 24 h (`expiresInSeconds: 86400`).

### Quota

Track `files_uploaded` (count) and `storage_bytes_uploaded` (cumulative bytes) in
`usage_records` alongside `emails_sent`. Quota limits per plan — suggested defaults:

| Plan | Max files/month | Max total MB/month |
|------|----------------|--------------------|
| Free | 10 | 50 MB |
| Starter | 100 | 500 MB |
| Growth | 1 000 | 5 GB |
| Pro | unlimited | unlimited |

The platform checks quota before every upload and returns 429 if exhausted.

### Shopify Files API

Not used. Files are delivered via signed URLs — in email bodies, as admin-UI download
buttons, or embedded in Shopify metafields by the handler. Uploading to Shopify's
CDN is a separate concern and out of scope for MVP.

### Concurrent uploads

GCS handles concurrent writes natively. No platform-side locking needed.

### Security

- The bucket has no public access. All reads go through platform-issued signed URLs.
- The platform signs URLs using the `api-sa` service account key (via ADC in Cloud Run,
  via `GOOGLE_APPLICATION_CREDENTIALS` in local dev if needed).
- fake-gcs supports V4 signed URLs for local testing.
