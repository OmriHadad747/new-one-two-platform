# Solution plan — TD-003 & TD-004

Both are platform-layer fixes that remove whole classes of LLM-drift and runtime-brittleness bugs in one stroke. TD-003 is a small, surgical template edit; TD-004 is a medium piece of generator infra with a few non-obvious tradeoffs. I'd land them as **two separate PRs** — they touch different trees, have different rollback profiles, and TD-003 must ship *before* the "don't retry Shopify" prompt rule so the rule isn't a lie.

---

## TD-003 — Shopify client 429 / 5xx retry

### Goal

Centralise rate-limit and transient-5xx retry discipline in the per-request Shopify helper at `platform-back/templates/handler/src/lib/shopify.ts`, so every generated handler inherits it. After this lands, the handler prompt can forbid the LLM from writing its own `setTimeout`/sleep loops — they'd fight the layer below.

### Design

**Retry wrapper** that decorates every upstream SDK call (`rest.get/post/delete`, `graphql`, the two `*paginate` iterators, and the `storefront` fetch). One shared helper keeps behaviour identical across verbs.

```ts
// Retry policy (hardcoded, not configurable — uniform across all handlers):
// - Max 4 attempts (1 initial + 3 retries).
// - Retry on: HTTP 429; HTTP 502/503/504; fetch-layer network errors (ECONNRESET,
//   ETIMEDOUT, getaddrinfo ENOTFOUND). Anything else bubbles as-is.
// - Delay for 429: Retry-After header if present (seconds OR HTTP-date, per RFC).
//   Absent/unparseable → exponential with full jitter starting at 500ms.
// - Delay for 5xx / network: always exponential with full jitter.
// - Backoff schedule: 500ms · 1s · 2s · 4s (cap). Full jitter = random_between(0, delay).
// - Absolute budget: 10s total sleep across all retries. Past that, throw.
// - 401 path is LEFT ALONE — with401Retry sits inside this wrapper's operation
//   closure and handles token refresh before we ever see a 429.
```

**Typed error on give-up** — a new `ShopifyRateLimitError extends Error` exported from the same module, so handlers can `catch` it specifically (e.g. to nack a BullMQ job for later retry instead of flushing the error log).

**Respect the SDK's 401 refresh path** — the existing `with401Retry` wraps the actual SDK call. The new retry wrapper sits one layer *above* `with401Retry`, so a 401 still refreshes the token exactly once, and a subsequent 429 still triggers the retry schedule. Nesting order: `withRetry(withTokenRefresh(sdkCall))`.

**Paginate iterators** — retry fires per page, not per stream. If the cursor page 7 of 50 throws 429, the iterator retries that one fetch; previously yielded pages stay yielded. The contract to the caller is unchanged.

### Concrete diff shape

`platform-back/templates/handler/src/lib/shopify.ts`:

1. Add `ShopifyRateLimitError` + `export` it near the top.
2. Add two helpers above `with401Retry`:
   ```ts
   function parseRetryAfter(h: string | undefined): number | null { /* seconds OR HTTP-date → ms */ }
   function classifyTransient(err: unknown): { status?: number; networkError: boolean } | null
   ```
3. Add `withRetry<T>(label: string, op: () => Promise<T>): Promise<T>` with the schedule above. It reads `globalThis.fetch`-agnostically — the `@shopify/shopify-api` SDK throws `HttpResponseError` (`code`/`response.code` on error objects) with `response.headers`, which is enough to pull `Retry-After`.
4. Wrap every `with401Retry(...)` body *and* the `storefront` fetch in `withRetry`. Five call sites total (`rest.get`, `rest.post`, `rest.delete`, `rest.paginate`'s each `rest.get` call, `graphql`, `storefront`).
5. Emit a single `console.warn({ label, attempt, delayMs, status, retryAfter })` per retry — structured so it's greppable in Cloud Run logs without polluting happy-path traces. No info-level chatter.

### Testing

- **Unit**: new `platform-back/templates/handler/src/lib/__tests__/shopify-retry.test.ts` with a mocked `api.clients.Rest` that sequences `[429 with Retry-After: 1, 429 with no header, 200]` → asserts three attempts, ~1s sleep on the first gap, jittered exponential on the second, final success.
- **Schedule cap**: inject `[429, 429, 429, 429]` → asserts throw-as-`ShopifyRateLimitError` after attempt 4 with total sleep < budget.
- **5xx**: `[503, 200]` → asserts one retry then success.
- **Non-retryable**: `[400]` → asserts one attempt, no sleep, error bubbles unchanged.
- **401 interop**: `[401, 200]` triggers the existing token-refresh branch without consuming a retry attempt.
- **Budget exhaustion**: verify we stop retrying when `Retry-After` would push total sleep past 10s — cuts off early with `ShopifyRateLimitError`.
- Use `vi.useFakeTimers()` so the test suite runs in milliseconds.

### Rollout

**Template change ⇒ takes effect on every *new* deploy.** Existing live handlers keep the old client. That's acceptable: the template is the compile-time source, not runtime infra. Add a note in the TD-003 close-out commit: *"Running apps pick this up on their next redeploy."* If we need to force-update live apps, it's a mass redeploy job — out of scope for this ticket, trackable as a sibling.

**Prompt rule ships in the same PR**, but worded to be true today:
> `shopify.rest.*` and `shopify.graphql` already handle 429 and transient 5xx internally with `Retry-After` + jittered exponential backoff. Do not add `setTimeout`, `Promise.resolve`-based sleep loops, or retry wrappers around Shopify calls. If a call gives up after the internal budget, catch `ShopifyRateLimitError` from `@platform-back/handler/shopify` and surface it — do not swallow.

Add that to `platform-ai/subagents/prompts/topics/handler.py` (or wherever the handler capability prompt lives — grep for the existing Shopify section).

### Affected files (final list)

- `platform-back/templates/handler/src/lib/shopify.ts` — retry wrapper + typed error export.
- `platform-back/templates/handler/src/lib/__tests__/shopify-retry.test.ts` — new file.
- `platform-ai/subagents/prompts/topics/handler.py` — prompt rule.

### Complexity

~200 LoC across two files, ~90 minutes of work + ~60 of tests. Zero migrations, zero prod coordination.

## TD-004 — Compile the generated handler during generation

### Goal

Catch type errors (`shopify.rest.get` signature mismatches, stale `ctx.*` method names, bad `await`, missing imports) during generation instead of at deploy-time, so they feed into the existing revision loop instead of burning a 3-minute deploy per miss.

### Architecture

**Generator-side Node sidecar.** The compile check runs inside the Python generator worker (where `crew.py` orchestrates the phases), shelling out to `tsc --noEmit` against a **pre-warmed sandbox** that mirrors `platform-back/templates/handler/`. The sandbox exists at container build time; each generation run drops the emitted files into `src/routes/`, runs tsc, parses output, tears the dropped files down. No install per run.

Three decisions up front that shape the design:

1. **Python→Node boundary.** We ship Node **inside** the platform-ai container. Avoids cross-container RPC (latency) and cross-process complexity. Python `subprocess.run(["node_modules/.bin/tsc", "--noEmit", ...])` is the whole bridge.
2. **Pre-warmed `node_modules`.** The difference between 3s and 30s per run. Baked into the Docker image at build time; never installed at runtime. Keeps generator boot fast, makes each compile deterministic (pinned versions), removes the cold-start spike on the first generation of a new pod.
3. **Isolation via temp working directory, not per-run install.** Each `compile_handler_artifact` call:
   - Creates a `tempfile.mkdtemp()` scratch dir.
   - Symlinks (not copies) `/app/handler-sandbox/{node_modules,tsconfig.json,package.json,src/server.ts,src/lib,src/middleware,src/migrate.ts}` into it — read-only.
   - Writes the generator output (`src/routes/*.ts` from the handler bundle, `migrations/<ts>_generated.sql` skipped because SQL isn't tsc's concern) into the scratch dir.
   - Runs `tsc --noEmit --pretty false --project tsconfig.json` with a 30s timeout.
   - Parses stdout.
   - Deletes the scratch dir (finally block, even on failure).

   Symlinking `node_modules` is the trick — tsc resolves through the symlink, so we get the full module graph without a 200 MB copy per run.

### Error parsing

tsc's `--pretty false` output is stable and line-oriented:

```
src/routes/orders.ts(42,18): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

Parser is ~15 lines of regex + dedup. Return shape matches the existing `static_errors` dict so the revision agent's consumer code is identical:

```python
# Keyed by generator name the same way static_errors already is.
# Since tsc errors live in the handler bundle, the only key is "handler".
# Widget/admin JS is compiled by a separate path (ESM + different tsconfig)
# and is out of scope for the first landing; see §Extensions.
{"handler": [
    "src/routes/orders.ts:42:18: TS2345: Argument of type 'string' not assignable to parameter of type 'number'",
    ...
]}
```

### Crew integration

New `_phase_compile` inserted **after static validation, before LLM validator**. Order rationale:
- Static validation is cheap (regex) → run first to fail fast on syntactic issues.
- Compile is medium (~3s) → run next, before paying the LLM validator round-trip.
- LLM validator is expensive (~10–20s + tokens) → only runs against code we *know* compiles.

Retry budget reuses the existing `_MAX_RETRIES=3` knob but shares it with static validation (a compile failure consumes a retry just like a static failure does). The revision agent already accepts `static_errors: Dict[str, List[str]]`; we reuse that exact channel — the revision prompt can't tell whether the error came from regex or tsc, and it doesn't need to.

Sketch:

```python
# crew.py inside _phase_codegen, after validate_artifacts:
error_map = validate_artifacts(artifacts, base_ctx, is_storefront, is_admin_ui)
if not error_map and get_settings().enable_compile_check:
    compile_errors = compile_handler_artifact(artifacts.get("handler", ""))
    if compile_errors:
        error_map = {"handler": compile_errors}
# Everything downstream — cumulative_errors merge, revision loop,
# _MAX_RETRIES cap, _fail_and_abort — is unchanged.
```

One subtlety: `_phase_codegen` currently treats `error_map` as "things the LLM should fix". Compile errors *are* that. But we shouldn't regenerate the handler from scratch on a tsc error — the static-validation retry loop already correctly routes to the handler-specific generator via `error_map.keys()`, so this falls out for free.

### Timeout + fallback handling

- **Subprocess timeout**: 30s hard cap. If tsc hangs (rare — pathological type recursion in generated code), kill it and treat as "compile errors were inconclusive → proceed to LLM validator." Log a warning with the artifact hash so we can reproduce offline. **Don't fail the generation on compile-infra flakes** — the LLM validator and deploy-time build are still behind us as backstops.
- **Node runtime missing / sandbox corrupted**: log error, skip phase, continue. The `ENABLE_COMPILE_CHECK` flag (see §Rollout) gives us a hard off-switch if this ever misbehaves in prod.

### Sandbox setup (the non-obvious part)

Build time — new stage in `platform-ai/Dockerfile`:

```dockerfile
# Node sandbox — used by crews/feature_generator/_phase_compile.
# We copy just what tsc needs to resolve imports and run typecheck,
# not the full handler template (no runtime assets, migrations, tests).
FROM node:20-slim AS handler-sandbox-builder
WORKDIR /sandbox
COPY platform-back/templates/handler/package.json platform-back/templates/handler/pnpm-lock.yaml ./
COPY platform-back/templates/handler/tsconfig.json ./
COPY platform-back/templates/handler/src ./src
RUN npm install -g pnpm@9.15.9 && pnpm install --prod=false --frozen-lockfile
# Smoke-test: the template itself must compile. If it doesn't, the sandbox
# is busted and every generation would fail — catch this at image build.
RUN pnpm typecheck

FROM python:3.11-slim
WORKDIR /app
# Install Node 20 for the compile check — Python base image has no Node.
# Use NodeSource script so we get the same major version as the sandbox.
RUN apt-get update && apt-get install -y --no-install-recommends curl \
 && curl -fsSL https://deb.nodesource.com/setup_20.x | bash - \
 && apt-get install -y --no-install-recommends nodejs \
 && rm -rf /var/lib/apt/lists/*
COPY --from=handler-sandbox-builder /sandbox /app/handler-sandbox
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ENV PORT=8001
EXPOSE 8001
CMD ["uvicorn", "api.server:create_app", "--factory", "--host", "0.0.0.0", "--port", "8001"]
```

Two-stage build keeps the runtime image small — we don't need pnpm in the final image, just the installed `node_modules`.

**Template drift protection**: the builder stage runs `pnpm typecheck` against the template's own source, so if someone breaks the template and doesn't notice, the generator image fails to build instead of silently producing bad compile errors for every downstream handler.

### Config + observability

- `ENABLE_COMPILE_CHECK` env flag in `platform-ai/config.py`, default `true` locally, **default `true` in prod** (the whole point is to catch errors before deploy). Kill-switch stays wired so we can toggle off without redeploy if the compile phase has a bad day.
- Per-run progress event: emit `_emit(request, "compile", "running", "Type-checking handler…")` → `"completed"` or `"retrying"`, same shape as the other phase events. The dashboard's SSE UI will render it automatically — no frontend work needed.
- Per-run latency + result logged to `agent_trace` (new entry kind `"compile"` with `latencyMs`, `retries`, `errorCount`). Lets us watch the phase's cost in ops dashboards.

### Testing

Three tiers:

1. **Unit** — `platform-ai/subagents/tests/test_compile_check.py`:
   - Happy path: known-good handler string → `[]`.
   - Type error: hand-crafted bad handler → specific `TS2345` in parsed output.
   - Missing import: → `TS2304` parsed.
   - Timeout: mock subprocess that sleeps 31s → returns `[]` (inconclusive, not failure) + logs warning.
   - Malformed tsc output: feed garbage stdout → parser doesn't crash, returns empty list.
2. **Integration** — `crew.py` with a real `_phase_compile` call, but with the subprocess stubbed to return canned results. Asserts `error_map` merges correctly, retry loop fires, budget caps.
3. **End-to-end smoke** — one `chat_local.py --stop-after validator` run against a recorded prompt that's known to produce a type error (grep `test_prompts/` for one that historically failed deploy). Before TD-004: passes generation, fails deploy. After: fails generation with a surfaced tsc message, revision agent fixes it in the same run.

### Failure-mode analysis

What happens when each piece breaks:

| Failure | Blast radius | Mitigation |
|---|---|---|
| Sandbox `node_modules` drift from template | Compile errors lie (false positives / negatives) | Builder stage's `pnpm typecheck` smoke-test catches it at image build |
| tsc hangs on pathological LLM output | 30s per run wasted | Hard timeout + log-and-continue |
| Node not on PATH in prod | Every generation loses a phase | `ENABLE_COMPILE_CHECK=false` kill-switch |
| Compile error output is noisier than revision agent can parse | Revision whack-a-mole | Parser dedups identical errors; passes `file:line:message` format the agent has handled for static-validation errors for months |
| Generator run latency blows budget | Real user impact | Phase is capped at 2 retry rounds × 3s + 30s timeout = 36s worst case; acceptable against 3-min deploy-failure alternative |

### Extensions (out of scope for first landing, but worth noting)

- **Widget/admin JS compile check**: different config (ESM, bundled-to-string), different sandbox. Leave for a follow-up ticket — handler type errors are the 80% case per the TD doc.
- **Migration SQL validator**: SQL is already validated by `platform-back/packages/deployer/src/sql-validator.ts` at deploy time. Moving that into generation would be a sibling to TD-004 but isn't in scope here.
- **Caching the sandbox per-pod**: the first compile warms the filesystem cache; subsequent compiles are ~1s. If that's not fast enough, we could keep a long-lived tsc `--watch` process with IPC, but that's a 10× complexity jump for a 2× speedup. Skip until data says otherwise.

### Affected files (final list)

- `platform-ai/subagents/compile_check.py` — new: sandbox runner + output parser.
- `platform-ai/subagents/tests/test_compile_check.py` — new: unit tests.
- `platform-ai/crews/feature_generator/crew.py` — hook `_phase_compile` into `_phase_codegen` after `validate_artifacts`, merge into `error_map`, emit progress event.
- `platform-ai/config.py` — `ENABLE_COMPILE_CHECK` flag.
- `platform-ai/Dockerfile` — two-stage build with Node + handler sandbox.
- `platform-ai/subagents/prompts/topics/handler.py` — (optional) one-liner mentioning that tsc errors will be fed back so the LLM doesn't over-annotate trying to pre-empt them.

### Complexity

Real medium — not because any one piece is hard, but because four things have to line up: Docker multi-stage, symlink-based sandboxing, Python→Node subprocess, and a clean error format the revision agent can act on. Budget: ~1.5 days work, ~0.5 day tests, ~0.5 day Dockerfile iteration. Worth flagging: the Dockerfile change will make CI builds take ~2 min longer until layers cache.

## Sequencing

1. **TD-003 first** — smaller, zero infra changes, unblocks the handler prompt rule.
2. **TD-004 second** — depends on template being stable (same template the sandbox builds against), so landing TD-003 first means the TD-004 sandbox inherits the retry wrapper for free at build time.

Both should be behind a feature flag (`ENABLE_COMPILE_CHECK` for TD-004; TD-003 doesn't need one — the retry wrapper is pure additive behaviour with no new failure modes beyond what the SDK already produces).

### Open questions

1. **TD-003 retry budget — 10s absolute cap OK?** Shopify's own guidance is "honor Retry-After," which for a single burst can be up to 10s; our 4-attempt × exponential schedule lands near that. If the handler timeout budget is tighter (Cloud Run default is 60s, handlers run at 30s), 10s is already a third — worth confirming.
2. **TD-004 kill-switch default** — proposed `ENABLE_COMPILE_CHECK=true` in prod. Alternative: ship `false` and flip after a week of soak.
3. **TD-004 failure budget sharing with static validation** — currently reuses `_MAX_RETRIES=3`. If compile failures should have their own retry budget (so a tsc error doesn't also burn a static-validation retry), it's a small refactor.
